# iFrame — исследование: frame pacer с НУЛЕВОЙ добавленной задержкой ввода

## 1. Откуда вообще берётся задержка ввода

Путь кадра: **ввод → симуляция (CPU) → рендер-команды → очередь GPU → очередь Present → скан-аут**.

Задержку добавляют четыре механизма:

| Механизм | Суть | Кто виноват |
|---|---|---|
| **Очередь GPU** | CPU сдаёт кадры быстрее, чем GPU рендерит → кадр ждёт всех впереди | Неограниченный FPS при GPU-bound |
| **Очередь Present (swapchain)** | `MaximumFrameLatency` по умолчанию = 3 кадра в очереди | Драйвер/движок |
| **Удержание готового кадра** | Лимитер дожидается «своего» времени ПОСЛЕ того, как кадр уже отрендерен | Так работают почти все внешние лимитеры |
| **Дрожание таймера** | `Sleep(1)` при разрешении таймера 15.6 мс пересыпает в среднем на **13.1 мс** (джиттер 4.2 мс) | Windows по умолчанию |

Ключевой факт (замеры tier1settings): при разрешении таймера 0.5 мс пересып `Sleep(1)` падает до 0.5 мс / джиттер 35 мкс — улучшение в 26 раз. Любой пейсер на дефолтном таймере сам создаёт микростаттеры.

## 2. Разбор существующих решений (эмпирика wccftech, Cyberpunk 2077, лимит 120 FPS / 120 Гц)

| Решение | Как работает | Задержка | Ровность |
|---|---|---|---|
| VSync | ждёт vblank после готовности кадра | **52.1 мс** (худший) | самая ровная выдача |
| Внутриигровой лимитер | ждёт ПОСЛЕ кадра, ДО старта следующего | низкая | зависит от движка |
| NV Driver Max Frame Rate | перехват на уровне драйвера | низкая | средняя |
| **RTSS Async** (дефолт) | буферизует 1 кадр; ровные СТАРТЫ кадров | низкая+ | старты ровные, **выдача дёргается** (Unwinder: «start-to-start vs present-to-present») |
| **RTSS Front Edge Sync** | держит кадр до переднего края vblank | низкая+ | самая ровная выдача из тестированных |
| **Reflex Low Latency** | движок завершает кадр «точно вовремя» (just-in-time), управляет back-pressure CPU | **17.6 мс** (лучший) | средняя |
| Special K Latent Sync | двухфазный лимитер (enforcement_policy 4): предсказание времени рендера + распределение простоя | 20.8 мс | adaptive STDDEV 2.4 FPS (лучший баланс) |
| framepacer | аналог RTSS Front Edge Sync «в один клик», внешнее окно | «крошечный input lag» (их FAQ) | ровная |
| bevy_framepace | **sleep ПЕРЕД началом кадра** (input → render → present без ожидания) | ~0 | ровная |

## 3. Ключевой принцип нулевой задержки

**Ждать ДО работы над кадром — бесплатно. Ждать ПОСЛЕ завершения кадра — платно.**

- Кадр, ожидающий в очереди, построен по **старому** вводу → его задержка растёт на всё время ожидания.
- Если же «усыпить» игру **перед стартом кадра**, ввод сэмплируется как можно позже → кадр свежий, и на экране он оказывается сразу по готовности.
- Это ровно то, что делает Reflex (уровень драйвера) и bevy_framepace (внутри движка). **Ни один популярный внешний лимитер этого не делает** — все ждут на Present.

Прямое подтверждение актуальности: в SpecialK issue #57 предложено ровно это («вызывать ожидание после present, а не до — это устранило бы лаг»), Kaldaien ответил, что Latent Sync — «двухфазный лимитер», но полностью проблему предсказания не решил.

## 4. Наш подход: JIT-пейсинг старта кадра (ядро iFrame)

Хук на `IDXGISwapChain::Present/Present1` (инъекция, как RTSS/framepacer):

```
Игровой цикл:  [симуляция+рендер кадра N] → Present(N) → [симуляция+рендер кадра N+1] → Present(N+1) → ...
                                        ▲                         ▲
                              мы НЕ задерживаем          мы задерживаем ВОТ ЗДЕСЬ
                              (кадр уходит на экран      (сон внутри хука ПОСЛЕ выполнения
                               немедленно)                реального Present)
```

Алгоритм на каждый вызов Present:
1. `t_done = QPC()` — кадр N готов.
2. **Сразу выполняем реальный Present** — кадр N никогда не удерживается (нулевая добавка для него).
3. Предсказываем длительность кадра N+1: `d = EMA(t_done - t_release)` — мы знаем оба времени, т.к. сами отпускали игру.
4. Вычисляем время старта кадра N+1: `t_next = следующий_vblank − d − safety` (just-in-time, как Reflex).
5. Гибридный сон до `t_next` (waitable high-res timer + спин на последних ~0.5 мс по QPC).
6. Возврат из Present → игра начинает кадр N+1 по **свежему** вводу.

Результат:
- **present-to-present = ровно один интервал** (идеальная ровность, как у Front Edge Sync);
- задержка ввода = только время рендера кадра `d`, **0 мс добавки**;
- в среднем на **пол-интервала МЕНЬШЕ задержки**, чем у uncapped+VSync, и до интервала меньше, чем у Front Edge Sync (мы ждём до кадра со свежим вводом, а не держим кадр с устаревшим).

Математика: uncapped+VSync: `латентность = d + interval/2` (ожидание vblank в среднем полпериода). JIT: `латентность = d`. 

Дополнительно: `IDXGIDevice1::SetMaximumFrameLatency(1)` на первом Present — режет очередь Present до 1 кадра (работает на ЛЮБОМ свопчейне, не требует флагов при создании; форсировать `FRAME_LATENCY_WAITABLE_OBJECT` через хук CreateSwapChain — опасная опция v2).

### Проблемы предсказания (из issue #57) и наши ответы
- **Ранняя готовность кадра** (предсказали с запасом): кадр дождётся vblank — это делает VSync, ровно как и без нас; добавки нет.
- **Поздняя готовность**: кадр уходит на следующий vblank — то же, что было бы и без лимитера; мы никогда не усугубляем (если опоздали — отпускаем немедленно).
- **Игра не тянет целевой FPS**: лимитер полностью инертен (телеметрия показывает «unlimited»).

## 5. Высокоточный тайминг
- `NtSetTimerResolution(0.5 мс)` на время работы пейсера (откат на выходе), fallback `timeBeginPeriod(1)`.
- `CreateWaitableTimerExW(CREATE_WAITABLE_TIMER_HIGH_RESOLUTION)` + спин-wait по QPC на финишных ~0.3–0.5 мс.
- Все временные метки — QPC.

## 6. Определение фазы vblank
- **DwmGetCompositionTimingInfo** — даёт QPC последнего vblank и частоту (работает для borderless/flip — как у framepacer, borderless и требуется).
- Уточнение: `D3DKMTGetScanLine` / `D3DKMTWaitForVerticalBlankEvent` (так делает SpecialK).
- Fallback: частота от пользователя + оценка фазы по истории present-меток.

## 7. Архитектура приложения

**Стек: Rust** (единственный установленный нативный тулчейн: rustc/cargo 1.95; MSVC cl отсутствует; CMake/.NET есть, но Rust покрывает всё). Плюсы для задачи: memory-safe код внутри чужого процесса (крах DLL = крах игры, безопасность критична), один язык для DLL + инжектора + UI, зрелые крейты (`windows`, `retour` для хуков, `egui` для UI). Открытый и бесплатный на 100%.

```
┌────────────────────────────────────────────────────┐
│ iframe.exe (UI + инжектор + детектор игр)          │
│  • egui-окно: цель FPS, график фреймтаймов,        │
│    профили per-game, хоткеи, трей                  │
│  • инжектор (LoadLibrary → удалённый поток)        │
│  • чёрный список античитов (EAC/BattlEye/Vanguard) │
└──────────────┬─────────────────────────────────────┘
               │ shared memory (ring buffer телеметрии)
┌──────────────▼─────────────────────────────────────┐
│ iframe_hook.dll (инъекция в игру)                  │
│  • хук Present/Present1 (DXGI: D3D10/11/12)        │
│  • JIT-пейсер: реальный Present сразу → сон после  │
│  • SetMaximumFrameLatency(1)                       │
│  • фаза vblank через DWM/D3DKMT                    │
│  • телеметрия: t_release, t_present, t_vblank      │
└────────────────────────────────────────────────────┘
```

**Режимы работы:**
1. **ZeroLag** (ядро) — наш JIT-пейсинг, полностью заменяет внутриигровой лимитер; VSync/VRR включается в игре для бесконтearной выдачи.
2. **Дополнение** — внутриигровой лимитер остаётся (кап чуть выше цели), мы только выравниваем выдачу и режем джиттер.
3. **Только телеметрия** — без инъекции вообще (ETW/PresentMon-подобный мониторинг): 100% античит-безопасно, график + рекомендации настроек.

**Валидация (доказательство нулевой задержки):**
- PresentMon (ETW) метрики: `msInPresentAPI ≈ 0` (кадр не держится внутри Present), `msBetweenPresents` — плоский, `msUntilDisplayed → 0`.
- Собственный тестовый D3D11-стенд + автотесты: расплывание фреймтаймов < порога, отсутствие хвостов.
- Сравнение с RTSS/framepacer на одном стенде.

## 8. Ограничения (честно)
- **Back-pressure CPU**: внешний лимитер не управляет им так, как Reflex внутри движка (потолок подхода — между NULL и Reflex). Частично компенсируется `MaxFrameLatency(1)`.
- **Frame Warp** (ресэмпл мыши перед скан-аутом) — недостижим извне, только драйвер/движок.
- **Античиты**: инъекция = риск в онлайн-играх → чёрный список + режим «только телеметрия».
- **Многопоточные движки** с глубоким пайплайном: пейсинг через Present работает через back-pressure; с `MaxFrameLatency(1)` глубина очереди = 1, трансляция точная.
