## Найденные проблемы

### 🔴 Баг 1 (тест красный): `pid_from_window_title("")` находит окно
`cargo test` падает: `l2_boundary_window_title_empty_and_special`.
Причина: `FindWindowW(NULL, "")` возвращает хэндл (совпадение по классу), функция возвращает Ok.
Файл: crates/iframe-app/src/injector.rs, `pid_from_window_title`. Фикс: отклонять пустой/blank title до FindWindowW.

### 🟡 Баг 2 (визуальный, не функциональный): DWM врёт о герцовке
`DwmGetCompositionTimingInfo` вернул 240 Гц при фактических 120 Гц монитора → лимитер 40 FPS дал ~112–136 FPS.
С `--refresh 120` (CLI) — точно 40. В UI поле refresh не задаётся (push_config всегда 0.0) — пользователь не может починить.
Файлы: crates/iframe-hook/src/vblank.rs, crates/iframe-app/src/ui.rs (push_config).

### 🟡 Наблюдение 3: «NEGATIVE LATENCY» в bench — маркетинговая арифметика
Формула «3 × frametime» для очереди DXGI — теоретическая модель, не измерение.
Реально измеренные факты (Present Hold ~0.03 мс, ровный каденс 40 FPS, late=0) корректны;
вывод «быстрее, чем без лимитера» — интерпретация, а не факт. Заявление README «+0 latency» честно.

### 🟢 Мелочи
- `iframe.exe --help` не печатает usage (падает в `unknown command`); `bench` не указан в usage.
- Лог хука: кириллица µs превращается в «Вµs» (OEM-кодировка), мусор от параллельных записей.
- README: x86 DLL называется `iframe_hook32.dll` в коде, сборка описана верно; OpenGL/Vulkan хуки в README не упомянуты.

## Числа из живых прогонов
